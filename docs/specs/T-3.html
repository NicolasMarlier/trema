Une interface pour piloter Trema

La tâche n'a pas de description. Trema est aujourd'hui un CLI bash (trema init / logs / env / console / destroy…) + un hook post-receive qui déploie via Docker Compose et nginx sur un VM. Je fais l'hypothèse que « Interface » = un tableau de bord web pour voir et opérer les apps hébergées, sans SSH. Une alternative TUI est proposée en question Q1.

Objectif

  • Voir d'un coup d'œil toutes les apps du serveur : statut des conteneurs, URL, dernier déploiement, ressources.
  • Faire depuis le navigateur ce qui nécessite aujourd'hui trema … + SSH : logs en direct, édition des variables d'env + redéploiement, redémarrage, dumps DB.
  • Garder l'esprit « léger, auto-hébergé » : un seul conteneur de plus sur le VM, pas de base de données propre (l'état est lu depuis ~/apps, ~/repos, Docker et nginx).

Architecture

  • trema-ui : petit service (Hono + React/Vite, conforme à la stack) déployé sur le VM par une nouvelle commande trema ui:install.
  • Lecture d'état : Docker (statut, stats, logs en streaming SSE), fichiers ~/apps/<app>/.env, configs nginx pour l'URL.
  • Historique des déploiements : le hook post-receive ajoute une ligne (date, commit, durée, résultat) dans un fichier deploys.log par app — seul changement au flux existant.
  • Actions : réutilisent les mêmes opérations que le CLI (docker compose up --build --force-recreate, pg_dump…), pour qu'il n'y ait qu'une seule façon de faire.

Hors périmètre (V1)

  • Création d'app depuis l'UI (trema init reste côté CLI : il touche au repo git local).
  • Multi-utilisateurs / rôles, multi-serveurs.
  • Métriques historisées (graphes) — cf. l'idée « Observability » du README.
Sécurité : l'UI a accès au socket Docker et aux secrets .env = équivalent root sur le VM. D'où la recommandation de ne pas l'exposer publiquement par défaut (Q2).
