Initialiser une nouvelle app depuis l'interface

Aujourd'hui, créer une app impose de lancer trema init depuis le poste local, dans le dossier git de l'app. La commande crée le repo bare sur le VM, copie le hook, écrit le vhost nginx, lance certbot, puis ajoute le remote trema et le fichier trema.env en local. L'objectif est de faire la partie serveur depuis le tableau de bord. L'UI affiche ensuite les commandes à lancer en local pour faire le premier git push trema main.

Périmètre proposé

  • Un bouton « + Nouvelle app » dans la barre latérale ouvre une fenêtre qui ne demande qu'un champ : le nom. Le domaine est calculé à partir du nom : <nom>.<host>.
  • La création tourne en job asynchrone, comme redémarrer ou redéployer, avec ses étapes et sa sortie suivies en direct (SSE).
  • À la fin, l'app apparaît dans la liste avec l'état « En attente du premier déploiement ». Sa page affiche les commandes à copier pour le poste local.
  • Le premier push suit le chemin actuel : le hook post-receive détecte un docker-compose.yml, sinon il applique le template Rails, puis crée .env et démarre l'app. Rien ne change dans le hook.
  • Hors périmètre : supprimer une app depuis l'UI, cloner depuis une URL GitHub, choisir un template de départ (voir Q1).

Workflow

Points techniques

SujetProposition
NomRègle plus stricte que l'actuelle, car le nom sert aussi de sous-domaine : ^[a-z0-9][a-z0-9-]{1,39}$. Le nom est refusé s'il existe déjà dans ~/repos, ~/apps ou un vhost nginx.
Liste des appsAujourd'hui, la liste se lit dans ~/apps/*, qui n'existe qu'après le premier push. La liste réunira ~/repos/* et ~/apps/*. Une app qui a un repo mais pas encore de dossier apps a le statut pending.
Hookui:install envoie aussi hooks/ sur le VM. Le serveur UI copie donc toujours la version actuelle du hook.
DroitsL'UI tourne sous l'utilisateur Trema. Le vhost s'écrit déjà sans sudo (le hook le fait). certbot exige root : voir Q3.
DNSIl faut un enregistrement wildcard *.<host>, sinon certbot échoue. Le message d'erreur l'indique.
SécuritéMêmes protections que les autres POST (en-têtes, CSRF, session et TOTP). L'action est inscrite dans audit.log. Une seule création à la fois.
TestsTests unitaires de la validation du nom, de la génération du vhost et de la fusion repos/apps. Test d'intégration de la route avec TREMA_HOME et TREMA_NGINX_SITES temporaires, certbot simulé.
