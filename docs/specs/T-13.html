Déployer sur push GitHub (façon Vercel), avec dossier racine

Rappel : une app Trema se déploie aujourd'hui uniquement par git push trema main. La v1 de cette spec proposait un webhook et une deploy key par app, avec un dossier racine (backend/, frontend/) pour qu'un monorepo alimente plusieurs apps. Toutes les recommandations ont été retenues. La v2 répond à la remarque « creuser une GitHub App au lieu du webhook + deploy key ».

Webhook + deploy key ou GitHub App ?

A · Webhook + deploy key (v1)

Pour chaque app, l'utilisateur copie trois éléments dans GitHub : l'URL du webhook, le secret et la deploy key.
  • ✓ Simple à coder, aucun appel à l'API GitHub.
  • ✓ Marche sans droits d'admin sur l'organisation (admin du dépôt suffit).
  • ✗ Trois copier-coller par app, et deux de plus par dépôt de monorepo.
  • ✗ Une deploy key ne sert qu'à un seul dépôt. Un monorepo qui alimente deux apps demande donc deux clés et deux webhooks.
  • ✗ Pas d'accès à l'API : pas de sélecteur de dépôt, de liste des branches ou de statut de commit.

B · GitHub App propre à l'instance Trema (reco)

On la crée une seule fois depuis Trema, en un clic, grâce au manifest flow de GitHub. On l'installe ensuite sur un compte en choisissant les dépôts.
  • ✓ Un seul webhook, configuré automatiquement, pour tous les dépôts installés.
  • ✓ Dépôts privés lus avec un jeton d'installation valable 1 h. Aucune clé par app.
  • ✓ Dans l'onglet Source, le dépôt et la branche se choisissent dans une liste, sans saisie libre.
  • ✓ Le statut ✓/✗ sur le commit coûte peu (Q12).
  • ✗ Plus de code : JWT RS256 (Node crypto, sans dépendance), échange de jetons, deux callbacks OAuth.
  • ✗ Clé privée de l'App à stocker sur la VM. Pour installer l'App sur une organisation, il faut en être admin.
Référence : Coolify propose les deux (« GitHub App » par défaut, « Deploy key » en secours). Pour un Trema mono-utilisateur, on recommande B seule : un seul chemin à maintenir. Si un dépôt ne peut pas recevoir l'App, il reste git push trema (Q5).
