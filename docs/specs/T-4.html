Usine · trema · T-4 · Spec

Une meilleure interface pour trema ui

Pas de description. Constat : T-3 a livré le tableau de bord fonctionnel (API + ui/public/index.html), mais le front est resté brut — boutons natifs empilés, tout sur une seule page, alert(), aucun retour pendant les actions, statut degraded/unknown non stylé, valeurs d'env envoyées en clair dans des <input type=password>. Je fais l'hypothèse que « Better UI » = amener le vrai front au niveau du prototype validé en T-3, et le rendre agréable à utiliser au quotidien. Pas de nouvelle fonctionnalité métier lourde.

Objectifs

  • Structure : barre latérale (apps + statut) / en-tête d'app (statut, URL, actions) / onglets Vue d'ensemble · Logs · Env · Déploiements. URL avec ancre (#/blog/logs) pour garder sa place au rechargement.
  • Retour utilisateur : boutons désactivés + statut « en cours » pendant une action, toasts (succès / erreur) à la place de alert(), confirmation pour les actions destructives (Arrêter, Enregistrer & redéployer).
  • Statut vivant : rafraîchissement auto de la liste toutes les ~10 s ; 4 états visibles (en ligne, dégradée, arrêtée, inconnue).
  • Logs : terminal sombre, suivi auto / pause, filtre texte, coloration warn/error, vider.
  • Env : tableau, valeurs masquées par défaut et révélées à la demande, suppression de variable, lignes modifiées marquées, récapitulatif des changements (ajout / modif / suppression) avant redéploiement.
  • Déploiements : tableau, dates relatives (« il y a 2 h »), pastilles réussi / échec, durée lisible.
  • Thème : palette Usine, clair/sombre suivant le système (+ bascule), états vides et erreurs (Docker indisponible, app sans conteneur).

Approche technique

SujetProposition
FrontReste un fichier statique sans build ni dépendance (cohérent avec trema ui:install = rsync, « sans dépendances »). JS vanilla structuré en petits modules (état, rendu par onglet, API).
Logique testéeFormatage (dates relatives, durées, mémoire), diff d'env (ajout/modif/suppr.), coloration de logs → fonctions pures dans un module partagé, testées avec node --test comme test/lib.test.mjs.
APIInchangée par défaut. Ajouts optionnels selon Q3/Q4 : URL publique de l'app (lue dans la conf nginx), ressources du VM, message de commit dans deploys.log, masquage des secrets côté serveur.
Hors périmètreNouvelles actions (dumps DB, suppression, console), multi-serveurs, graphes historisés.
Sécurité : aujourd'hui GET /env renvoie toutes les valeurs ; le « masquage » n'est qu'un type=password. lib.mjs contient déjà maskEntries/isSecretKey inutilisés. Je propose d'en profiter (Q4).
