Télécharger et restaurer un dump de base de données

Depuis l'interface web, pour chaque app qui a une base Postgres : créer et télécharger un dump, et envoyer un dump pour remplacer la base, que le schéma du dump soit identique à l'actuel ou non. Aujourd'hui, ça passe seulement par le CLI (trema archive_db, trema load_pg_dump), en SSH, avec des dumps data-only rejoués tels quels par psql, sans filet de sécurité.

Proposition en bref

⬇ Télécharger

Un nouvel onglet Base de données liste les dumps de l'app dans /db_dumps (taille, date, origine). « Créer un dump » lance un job pg_dump (complet : schéma + données) suivi en direct, comme les autres jobs. Chaque dump a un lien « Télécharger » (session requise, action inscrite dans audit.log).

⬆ Restaurer

On envoie un fichier (.dump, .sql ou .sql.gz) ou on choisit un dump existant, puis on choisit un mode : Remplacer tout (on prend le schéma du dump, puis on joue les migrations de l'app) ou Données seulement (on garde le schéma actuel, on vide les tables puis on recharge). Un dump de sécurité est pris automatiquement avant, et on confirme en tapant le nom de l'app.

Les deux modes de restauration

« Avec ou sans changement de schéma », tel que je le comprends :

ModeQuand l'utiliserCe qui se passe
Remplacer tout
avec changement de schéma		Le dump vient d'une autre version de l'app (plus ancienne, Heroku, autre environnement), ou d'une base vide.Le schéma public est supprimé et recréé, le dump complet est restauré, puis les migrations sont jouées (bin/rails db:prepare) pour aligner le schéma sur le code déployé.
Données seulement
sans changement de schéma		Le dump a le même schéma que la base actuelle (export d'une autre instance de la même version).Toutes les tables sont vidées (sauf schema_migrations et ar_internal_metadata), puis seules les données sont chargées. Si une colonne ne correspond pas, tout est annulé (une seule transaction).
