Documenter l'architecture de Trema

Description : « What's centralize or not, etc. » Je comprends qu'il faut une page de doc qui explique où vit chaque élément de Trema : sur le poste du développeur, sur le VM et partagé par toutes les apps, ou sur le VM et propre à une app. Elle doit aussi expliquer les flux principaux (init, déploiement, env, UI). Cette tâche ne demande que de la doc : on ne change pas le code.

Objectif

  • Une personne qui découvre le repo comprend en 5 minutes ce qui tourne où, et ce que chaque commande trema touche.
  • On répond clairement à « qu'est-ce qui est centralisé ? » et on montre les points sensibles. Exemple : le hook est copié dans chaque app, donc il faut un trema update pour mettre une app à jour.
  • La doc est en français (conventions), dans le repo, et le README pointe vers elle.

Contenu prévu du document

SectionContenu
1. Vue d'ensembleTrema = CLI bash + un VM (nginx, certbot, Docker) + une UI Node optionnelle. Un seul VM, un seul utilisateur, aucune base de données de Trema.
2. Où vit quoiCarte en 3 zones (voir le prototype ci-dessous) et tableau des fichiers et chemins.
3. Centralisé ou par appCe qui est partagé, ce qui est isolé par app, ce qui est copié (et peut donc être en retard de version).
4. Fluxtrema init, git push trema main, trema env / UI, trema update, destroy.
5. Réseau & sécuritéPorts (port web aléatoire → nginx, UI sur 127.0.0.1:4000), TLS, tunnel SSH ou accès web, où se trouvent les secrets.
6. Limites connuesComportement observé aujourd'hui, sans plan d'action (voir Q3) : un seul VM, Postgres par app sans sauvegarde automatique, pas de registre d'apps (la liste = ~/apps/*), template Rails figé.

Flux de déploiement (exemple de schéma)

Point clé à mettre en avant : sur le VM, centralisé ne veut pas toujours dire partagé à l'exécution. Les templates ~/docker_compose_files sont centraux, mais ils sont copiés dans apps/<app> à chaque déploiement. Le hook est copié une fois par app, à l'init et à l'update. La doc distinguera trois états : partagé par app copié depuis le central.

Livrable

  • Un fichier de doc (format et emplacement : Q1), avec des schémas (format : Q2).
  • Un lien depuis le README, et la section « Installation — TODO » renvoie vers la doc si Q4 = oui.
  • On ne change pas le code. Pas de tests (pas de logique métier).

Hors périmètre

  • Refactorer ce qui est copié (ex. un hook unique partagé) : ce sera une tâche à part si besoin.
  • Une doc utilisateur complète pour chaque commande (le usage du CLI suffit).
