Ouvrir l'interface Trema sur le web

Pas de description. Aujourd'hui, l'interface Trema (T-3) n'écoute que sur 127.0.0.1:4000 et on y accède par trema ui (tunnel SSH). Je pars du principe que « accessible depuis le www » veut dire : ouvrir l'interface en HTTPS sur un sous-domaine, protégée par une authentification, pour s'en servir depuis n'importe quel navigateur (téléphone compris) sans SSH. Une autre lecture possible (domaines perso pour les apps hébergées) est proposée en Q1.

Objectif

  • Ouvrir https://trema.<host> depuis n'importe où, s'identifier, utiliser le tableau de bord comme avant.
  • Rien n'est exposé sans le demander : une commande l'active (trema ui:expose), une autre la désactive (trema ui:unexpose).
  • Le tunnel SSH (trema ui) continue de marcher, sans authentification de plus.
  • Garder le style « léger » : pas de base de données, pas de dépendance npm, on réutilise le nginx et le certbot déjà en place pour les apps.

Prototype

🔒 https://trema.vm.example.com

Activation côté CLI

$ trema ui:expose Domaine [trema.vm.example.com] : Mot de passe (12 caractères min.) : •••••••••••••• ✅ vhost nginx trema.vm.example.com → 127.0.0.1:4000 ✅ certificat TLS (certbot) ✅ mot de passe enregistré (haché) dans ~/trema-ui/auth.json ✅ trema-ui redémarré → https://trema.vm.example.com $ trema ui:password # changer le mot de passe, toutes les sessions sont fermées $ trema ui:unexpose # supprime le vhost, retour au tunnel seul

Architecture

  • nginx : un vhost trema.<host> calqué sur celui des apps (add_nginx_config) + certbot, avec une limite de requêtes sur la route de connexion.
  • trema-ui écoute toujours sur la boucle locale uniquement. Il accepte aussi le domaine configuré comme Host/Origin. Une requête qui arrive par nginx (domaine public) doit avoir une session valide, sinon elle voit l'écran de connexion. Une requête sur localhost (tunnel) passe sans login, comme aujourd'hui.
  • Authentification : un seul mot de passe admin, haché (scrypt, natif dans Node) dans un fichier côté VM, et un cookie de session HttpOnly; Secure; SameSite=Strict signé. Pas de comptes multiples.

Parcours

Risque : l'interface a accès au socket Docker et aux secrets .env, donc la compromettre revient à être root sur le VM. Il faut donc : HTTPS obligatoire, mot de passe long, limite de tentatives, sessions révocables (trema ui:password) et retour possible au tunnel seul (ui:unexpose). Il faudra aussi mettre à jour la mise en garde « ne jamais l'exposer » du README.

Hors périmètre

  • Comptes multiples, rôles, SSO/OAuth.
  • Domaines personnalisés pour les apps hébergées (sauf si Q1 = b).
