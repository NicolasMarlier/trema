Rotation des logs sur la VM Trema

La tâche n'a pas de description : j'interprète « cron log rotation » comme empêcher les logs de remplir le disque de la VM. Aujourd'hui les conteneurs (web, db) écrivent sur stdout (RAILS_LOG_TO_STDOUT=enabled) via le driver Docker json-file par défaut, sans aucune limite : les fichiers /var/lib/docker/containers/*/*-json.log grossissent jusqu'à saturer le disque, et toutes les apps tombent en même temps. S'y ajoutent les dumps de /db_dumps, qui s'accumulent eux aussi.

Objectif

  • Plafonner l'espace disque occupé par les logs de chaque app (web + db), y compris les apps qui fournissent leur propre docker-compose.yml.
  • trema logs doit continuer de fonctionner (docker logs -f) et garder un historique récent exploitable.
  • Ne rien demander à l'utilisateur : la rotation est active par défaut, avec des réglages raisonnables et surchargeables.
  • Installation idempotente sur la VM, via une commande Trema (pas d'intervention manuelle en SSH).

Approches possibles

Recommandée

A. Rotation native Docker (sans cron)

Options du driver json-file : max-size / max-file. Posées par défaut au niveau du démon (/etc/docker/daemon.json) pour couvrir toutes les apps, et rappelées dans le template Rails.

+ Zéro processus à maintenir, rotation en continu, compatible docker logs.
− Appliqué seulement aux conteneurs recréés (OK : chaque déploiement fait --force-recreate). Modifier daemon.json impose un redémarrage de Docker, une seule fois.

B. Cron + logrotate

Une règle /etc/logrotate.d/trema (copytruncate, compression, rétention N jours) sur les fichiers JSON de Docker, lancée par cron toutes les heures.

+ Rétention exprimée en jours, archives compressées.
− Docker ne voit plus les archives (docker logs n'affiche que le fichier courant), risque de perte de lignes à la troncature, entre deux passages un pic de logs peut encore remplir le disque.

Dans les deux cas, on ajoute un cron quotidien de ménage de /db_dumps (dumps de plus de N jours) et un docker image prune / builder prune optionnel — voir Q3.

Simulateur : espace disque occupé

Stratégie :
Estimation simplifiée : volume par conteneur, ratio de compression gzip ≈ 10 % pour logrotate. Les dumps ne sont pas comptés.

Mise en place côté CLI

Nouvelle commande trema server:setup (globale, n'a pas besoin de trema.env si ~/.trema_config est renseigné), également appelée par trema update. Elle est idempotente.

$ trema server:setup
→ Connexion à deploy@vm.example.com
✅ /etc/docker/daemon.json : log-driver json-file, max-size=20m, max-file=5
⚠  Docker doit redémarrer pour appliquer la config (≈10 s d'interruption de toutes les apps).
   Redémarrer maintenant ? [y/N] y
✅ Docker redémarré, 4 apps relancées
✅ Cron /etc/cron.d/trema-cleanup : dumps > 14 j supprimés chaque nuit à 03:30
ℹ  Les limites s'appliquent aux conteneurs recréés : elles seront actives au prochain 'git push trema main'.

$ trema logs --tail 200      # nouveau : sans -f, ou historique limité
